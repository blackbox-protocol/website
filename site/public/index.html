01See it workWhat it is, whether it's for you, and proof you can run yourself.

When something goes wrong, whose word do you have?

When an automated system does something you didn't expect, the account of what happened often comes from that same system.

  • An AI agent deletes the wrong records.
  • A deployment goes out that nobody approved.
  • A vendor's system says it did the thing it was paid to do.

In each case, the only account of what happened may come from the system that performed the action, or from a log that system controls.

Blackbox gives the action its own record: signed when it happens and checkable afterward without asking the system that produced it.

Connectors

Three concrete things it can sign today.

Each connector signs caller-supplied metadata for one kind of action. None of them call any external service.

AI agent actions

Signs agent action metadata: provider, model, action kind, input and output hashes, and timestamps.

HTTP requests

Signs request and response metadata: method, URL, requester id, response status, content type, scope, request id, and timestamps.

CI builds

Signs build metadata: repository, workflow, run id and attempt, job, commit, ref, event, actor, runner OS, status, timestamps — plus optional source-tree, artifact, and test-result hashes.

These three ship as examples. The underlying library signs any structured record you give it, so the pattern extends to whatever your software does.

Blackbox does not watch your system. It gives you a way to make its actions checkable by someone else.

Trust boundary

What a receipt does and does not establish

A receipt proves less than people assume — and stating that plainly is part of the design.

What a receipt establishes

The recorded claims were signed and have not been altered afterward.

What it does not establish

That the system creating those claims accurately described the outside world.

When you don't need Blackbox

If you control both sides of the system and already trust your logs, Blackbox may not add much.

It is most useful when the record needs to survive outside the system that created it.

Step 1 of 6 · Clone & build

Clone the repository, install dependencies with pnpm, and build every workspace. The compiled CLI lands at packages/cli/dist/cli.js.

git clone https://github.com/blackbox-protocol/blackbox.git
cd blackbox
pnpm install
pnpm -r build

No terminal output is published for this step.

Step 2 of 6 · Keys & payload

Generate an Ed25519 keypair and a trust-anchor bundle JSON (issuer demo-issuer, key version 0), then write a small payload.

mkdir -p ./demo
node -e "const c=require('crypto');const fs=require('fs');const {publicKey,privateKey}=c.generateKeyPairSync('ed25519');const sk=privateKey.export({format:'der',type:'pkcs8'}).slice(-32).toString('hex');const pk=publicKey.export({format:'der',type:'spki'}).slice(-32).toString('hex');fs.writeFileSync('./demo/key.hex',sk);fs.writeFileSync('./demo/bundle.json',JSON.stringify({bundleVersion:1,authorizedIssuers:[{issuerId:'demo-issuer',keyVersion:0}],publicKeysByKeyId:{'demo-issuer:0':pk},revokedKeyIds:[]},null,2));"
printf 'hello blackbox' > ./demo/payload.bin

This prints nothing. That means it worked.

Step 3 of 6 · Sign

Sign the payload. The signed receipt is written to ./demo/receipt.cbor.

node packages/cli/dist/cli.js sign \
  --payload ./demo/payload.bin \
  --key ./demo/key.hex \
  --issuer demo-issuer \
  --counter 0 \
  --bundle-version 1 \
  --output ./demo/receipt.cbor

Heads up: the receipt contains your whole file. Anyone you send a receipt to can read what you signed.

To sign your own file, replace ./demo/payload.bin with the path to your file, e.g. /c/Users/<you>/Documents/notes.txt

Step 4 of 6 · Verify

Verify the receipt against the trust bundle.

node packages/cli/dist/cli.js verify ./demo/receipt.cbor \
  --bundle ./demo/bundle.json \
  --signer-key-id demo-issuer:0

Look for: composite: PASS

You'll see an 'errors:' line with a replay note under PASS. That's normal: replay and chain aren't checked in this demo. It isn't a failure.

Step 5 of 6 · Tamper

Flip the last byte of the signature (XOR 0x01) into a tampered copy, then verify again.

node -e "const fs=require('fs');const b=Buffer.from(fs.readFileSync('./demo/receipt.cbor'));b[b.length-1]^=0x01;fs.writeFileSync('./demo/receipt.tampered.cbor',b);"

This prints nothing. That means it worked.

node packages/cli/dist/cli.js verify ./demo/receipt.tampered.cbor \
  --bundle ./demo/bundle.json \
  --signer-key-id demo-issuer:0 || true

Look for: composite: FAIL and SIGNATURE_INVALID

Step 6 of 6 · Inspect

Inspect the envelope structurally. inspect never verifies a signature; it reports envelope structure and protected-header values only.

node packages/cli/dist/cli.js inspect ./demo/receipt.cbor

The demo folder contains a private key (demo/key.hex). Delete the folder when you're done testing.

Performance

What does it cost?

Measured on one modest laptop, not guessed. The two numbers that matter are different, so they are kept apart.

Warm, in-process (library call)

  • ≈2.3 ms sign a 1 KiB receipt (p50)
  • ≈9.9 ms verify a 1 KiB receipt (p50)
  • ≈93.7 ms verify at 1 MiB (larger payloads cost more)

Startup-inclusive (CLI invocation)

  • ≈341 ms a CLI verify — includes Node startup, module load, and CLI init
  • ≈11.7 ms a durable file-backed replay accept (synchronous fsync + rename)

Measured on an HP ENVY x360 (AMD Ryzen 5 2500U, Node 22.22.2) with pure-JavaScript cryptography — a modest 2018 laptop. These are results from this specific machine and implementation, not a hardware-independent claim. A separate benchmark document records the full methodology, distributions, and raw samples.

Why not just sign a JSON blob?

For simple signing, you should.

Blackbox is for the work around the signature:

  • canonical bytes
  • structured verification
  • replay protection
  • chaining
  • revocation
  • strict parsing
  • and receipts other implementations can read

Verification surface

It tells you what it didn't check.

The verifier runs seven checks in a fixed order and reports each one on its own. It does not stop at the first failure.

  1. 1cryptographicThe Ed25519 signature verifies against the receipt.pass
  2. 2semanticThe envelope and its headers parse under a closed schema.pass
  3. 3authorizationThe signing key is a trust anchor for the declared issuer.pass
  4. 4temporalThe timestamp and counter fall inside the caller's window.pass
  5. 5revocationThe signing key is not in the revoked-key set.pass
  6. 6replayThis receipt's nonce and counter have not been used before in its stream.not_evaluated
  7. 7chainThe receipt commits to the previous receipt in its stream.not_evaluated

A composite PASS does not mean all seven passed.

LIMIT Replay and chain do not run without the context they require. Supply a tracker or chain context; otherwise they report not_evaluated instead of silently passing.

One verifier

We verify with the same code you do.

There is no separate vendor verifier. Issuer-side verification and external verification call the identical function.

The source contains no issuer-only verification shortcut. Confidence comes from reading the code and reproducing the evidence.

Determinism

Same bytes in. Same verdict out. Forever.

The verifier is a pure function. It has no clock, no random numbers, no timers, no network, and no file I/O.

  • A test enforces 16 forbidden patterns to keep it that way.
  • The temporal axis never reads the host clock, so a wrong system time can't change a verdict.
  • Your machine and an auditor's machine produce the identical result.

LIMIT Determinism is about the verdict, not the truth of the record. It guarantees a repeatable answer, not that the signed claims describe the world.

The gate

Refuse the action. Sign the refusal.

The gate can block an action fail-closed and sign the denial as evidence. It evaluates in a fixed five-stage precedence.

  1. 1configuration
  2. 2tracker availabilitymissing tracker → denial before verification
  3. 3verification
  4. 4policy
  5. 5allow

Example: a denied action

denial.cose

A valid signature alone never authorizes execution. Policy is always a separate step. There are four denial codes, and every denial is signed.

LIMIT The gate ships as a library, @blackbox/gate, with a policy callback. There is no gate CLI command and no policy file. The signed denial payload contains only the decision and the denial code — verdict detail is not signed. Only Mode 2 binds the denial to the intent receipt.

Chaining

Break the chain and it shows. Delete the end and it doesn't.

Each receipt commits to the previous receipt's content hash. Tampering with the middle of a chain produces a specific verification failure.

LIMIT Deleting the newest receipts cannot be detected without an outside witness, because nothing points forward. Detecting it requires a transparency log or a scheme with forward-secure key evolution — both future work. This limitation is shared by every self-contained chain.

Receipt hashes

Two hashes, on purpose.

A receipt has two hashes with different jobs, and using the wrong one would quietly break chaining.

Content hash
Cosign-independent. Chains link on this hash.
Envelope hash
Changes when a cosigner is added.

The envelope hash is explicitly forbidden for replay acceptance. If chaining used the envelope hash, adding a cosigner could silently break the chain relationship.

Deterministic CBOR

It rejects what sloppy parsers accept.

Deterministic CBOR per RFC 8949, enforced on both encode and decode.

non-shortest-form integers
indefinite length
tags
floats
duplicate keys
non-canonical key order
trailing bytes
nesting beyond 1,024

Also enforced Unprotected maps must be empty. Envelope arrays are closed by exact arity.

LIMIT Protected headers validate the labels they know and ignore unknown ones. The CDDL specification is stricter than the parser and is hand-maintained.

Reproducibility

Don't trust the binary. Rebuild it.

The shipped CLI rebuilds byte-identically from source: same OS, clean clone, compared by SHA-256.

  • no sourcemaps
  • no timestamps
  • no absolute paths

The browser bundle ships with no Node built-ins and stays under 250 KB.

LIMIT Same-OS rebuild verified manually, not in CI. Cross-OS byte identity is not claimed.

Provenance

We kept the failures.

Two records we kept because they show the process, not the polish.

A build that died, kept beside its fix

A run died on a missing Java dependency. The failed run is preserved byte-for-byte beside its correction.

  • missing dependency coordinates
  • size
  • checksum

The dependency was verified against Maven Central.

Three libraries disagreed, on the record

Three COSE libraries disagreed on the same input. The expectation was written down in advance, and the execution was separated into two roles:

  • runner only captured raw bytes
  • grader only graded

Each role demonstrated refusal to do the other's job.

cose-java · accepted go-cose · rejected pycose · rejected

RFC 9053 imposes no canonical signature-length requirement, so this is a standards-permitted interoperability difference.

Not a vulnerability. Not a CVE. No library is wrong.

The failures are part of the evidence. Removing them would make the project look cleaner and the record less useful.

03What it can't doThe boundaries, stated plainly — and where the project goes next.

Architecture

What's in the box.

At runtime your software calls one path. The evidence harness is a separate supporting layer — it is not something your software calls to verify.

Packages

  • @blackbox/core — signing + verification
  • blackbox — the CLI
  • @blackbox/gate — policy gate (source-visible)
  • @blackbox/evidence — test corpus / harness
  • connector: ai-agent
  • connector: http-request
  • connector: github-actions-build

Not published to npm yet. Build from source.

Honest limits

What it is not.

  • Not externally audited.
  • No formal verification.
  • Ed25519 only.
  • No post-quantum support.
  • Not compliance.
  • Not identity.
  • Not monitoring.
  • Not a blockchain.
  • Tamper-evident, not tamper-proof.
  • It does not protect a stolen key.
  • It does not make JavaScript signing constant-time.
  • It should not be exposed as a public signing endpoint.

A receipt establishes the integrity of the claims recorded in it. It does not establish that the recorder told the truth about the world.
